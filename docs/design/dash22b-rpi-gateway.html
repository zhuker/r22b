Dash22b ↔ Raspberry Pi in-car gateway — design sketch

Drafted 2026-09-13 from a chat exploration. Not a decision, not a plan — a design sketch to come back to when the Pi-side work is next on the bench. All Pi-related plans for the car live in this one file.

Goal

Move data collection off the phone and onto an always-on Raspberry Pi 4 in the glove box. Over time the Pi becomes the car's compute node: SSM polling against the 2005-STI ECU, BLE TPMS collection, rear-view camera, and BLE-based phone-as-key with walkaway auto-lock. Preserve the current "plug in, dash22b auto-launches" ergonomic. The dash22b Android app stays as the driver-facing display and control surface.

Phasing

Rolled up in dependency order. Each phase is deliberately self-contained so it can ship without waiting on the next.

Phase 1 — BLE door lock (isolated slice)

BLE-only, door-lock-only. Does not touch SSM, USB-serial, or camera. Ships as a fully independent feature.

  • Pi acts as a BLE peripheral, exposing one GATT vehicle-access service.
  • Phone app (dash22b module) locks/unlocks over BLE after crypto handshake.
  • Existing K-line USB-serial path to the phone remains untouched.

Phase 1.5 — Walkaway auto-lock

Additive on top of Phase 1 once the manual command path is proven reliable in all real-world states.

Phase 2 — Pi-mediated SSM/TPMS over USB-Ethernet

K-line USB cable moves off the phone and onto a Pi USB-A port. Pi owns the ECU link; phone talks to the Pi over TCP via a USB-C ↔ USB-Ethernet dongle through the existing PD Y-adapter.

Phase 3 — Rear-view camera

UVC camera on a Pi USB-A port, restreamed as MJPEG/H.264 over the same Ethernet link. Kept separate from the SSM transport code.

Phase 4 — Wi-Fi as a third transport

Pi joins home Wi-Fi in the garage or runs its own AP. Same socket code as Phase 2, different route. Enables pulling logs from inside the house and a cable-free fallback for the SSM stream.

Phase 1 — BLE door lock (v1 scope)

Deliberately small. Ships as its own feature without any refactor of the existing dash22b USB-serial pipeline.

What the Pi runs

  • Pi 4's onboard Cypress CYW43455 combo chip supports BT 5.0 + BLE. BlueZ 5 + bluetoothd handle peripheral mode natively on Raspberry Pi OS.
  • Userspace GATT server in Python (bluezero or dbus-next), Go (tinygo.org/x/bluetooth), or Rust (bluer) — all fine.
  • Range: onboard antenna is OK inside the cabin, marginal outside 10 m through metal roof + heated windshield. An external USB BT dongle with a real antenna extends useful walkaway range if Phase 1.5 needs it — Phase 1 (manual command) doesn't.

GATT surface — one service, four characteristics

CharacteristicAccessPurpose
lock-stateread + notifyReports "locked / unlocked" and last-changed timestamp.
auth-challengeread + notifyPi issues a fresh nonce.
auth-responsewritePhone signs the nonce with its per-vehicle key; Pi verifies.
commandwriteAccepts lock / unlock after a valid auth-response.

Phone side (dash22b module)

  • Small BLE client + unlock UI. No SSM/USB-serial code involved.
  • Per-vehicle signing key stored in Android Keystore (hardware-backed on modern phones), gated by biometric before signing.
  • v1a can be manual-only: tap unlock in the app or a persistent notification action. No RSSI heuristics yet.

Hardware — the load-bearing half

The BLE + crypto is a weekend of code. The door-lock wiring is what has to be right the first time.
  • Tap point on the '01 body: drive the same control lines the OEM RKE receiver drives, not the door actuators directly — the factory timer handles pulse duration and current. FSM WIRING SYSTEM SECTION has the door-lock timer + keyless entry receiver pinout.
  • Relay board with hardware watchdog: an enable line the Pi must refresh every N ms or the outputs go safe. Guards against Pi crash / hang / malicious input holding an output stuck.
  • Fuse on the relay coil supply, on its own circuit that doesn't take out anything else if it pops.
  • OEM key still works. The DIY path is additive, never the sole entry method.

Security bar for v1

  • Bonded pairing with an out-of-band first-pair step (a code shown on the phone that gets typed into a Pi-side web UI, or vice versa). Reject unbonded peers on the vehicle-access service.
  • Rolling challenge-response on every unlock. Nonce from Pi, Ed25519 signature from phone, Pi verifies with the paired public key. Do not rely on "the connection is encrypted, that's enough" — it isn't, especially against relay attacks.
  • Biometric-gated signing on the phone side, so a stolen unlocked phone still won't unlock the car unless the attacker also authenticates.
  • Rate-limit failed responses (3 fails in a minute → 5 min backoff).
  • Known residual risk: BLE relay attacks. Real mitigation is UWB or accelerometer-aided distance bounding — a future-phase problem, not v1.

Phase 1.5 — Walkaway auto-lock

Tesla's phone-key uses BLE RSSI + a proximity model (and on newer cars, UWB ranging), not just "connected or not." The car estimates distance from the phone by watching signal strength over time; walkaway triggers when estimated distance crosses a threshold for a sustained window.

Two implementation paths

  • Pi as peripheral, phone connects and holds: Pi tracks connection state + RSSI. When RSSI drops below a threshold for N seconds and the phone was previously "inside range" for M seconds, trigger lock. When the phone comes back into strong range and passes auth, unlock. Cheap; RSSI is noisy so tuning is real.
  • Phone as advertiser (iBeacon/Eddystone), Pi scans: phone advertises a stable UUID, Pi estimates distance from ad RSSI. Better for phone battery, matches how commercial phone-as-key systems work. Android handles background BLE ads fine (dash22b is Android-only, so no iOS quirks to work around).
  • Optional second antenna: an ESP32 with a real antenna on the rear bumper gives two spatially-separated RSSI readings; a Kalman filter over both makes "inside vs. outside the car" much more reliable without UWB.

Recommend deferring this until Phase 1 has been proven reliable on manual command in every real-world state (parked-uphill, cold-soak, low-battery, etc.).

Phase 2 — SSM/TPMS over USB-Ethernet

Today's baseline

  • Phone (dash22b) ↔ USB serial K-line cable (FTDI/CH340/CP210x) directly to the car's diagnostic port.
  • Android auto-launches dash22b on USB_DEVICE_ATTACHED matching the cable's VID/PID in device_filter.xml.
  • usb-serial-for-android handles the wire protocol.
  • Existing PD Y-adapter (Amazon order 112-4102290-8091436, delivered 2026-01-19, ~$10): "2-in-1 USB C OTG Adapter and Charger" with 60W PD passthrough. Phone charges + data-USB works simultaneously through one physical port.

Chosen architecture

Phone → PD Y-adapter → USB Ethernet dongle → RJ45 → Pi 4 built-in gigabit port. The Y-adapter is reused unchanged. The K-line USB cable moves off the phone and onto one of the Pi's USB-A ports.

Why this shape

  • Pi 4 stays 100% normal. All four USB-A ports free for K-line cable, rear-view camera, GPS, USB storage. USB-C port is power-in only. No dwc2 / configfs gadget config, no RNDIS quirks, no composite-device gymnastics.
  • Pi 4 has real gigabit Ethernet on its own PCIe-attached MAC (not USB-shared like the Pi 3). Independent of everything USB.
  • The RJ45 on the Pi is still free for dev while the phone is connected via the dongle — sit in the driveway with a laptop on the Ethernet jack, SSH in, tail logs.
  • Auto-launch works the same way as today. Android fires USB_DEVICE_ATTACHED for USB Ethernet dongles (the phone sees the dongle's VID/PID before the kernel claims it as a network interface). Pin a dongle chipset (RTL8153 = 0bda:8153, or AX88179 = 0b95:1790), add that VID/PID to device_filter.xml, and plugging the cable in wakes dash22b exactly like the FTDI cable does today.
  • Charging is already solved by the existing Y-adapter — the "phone port is busy, so it can't charge" problem doesn't apply.

Not chosen (and why)

  • Pi 4 in USB gadget mode (RNDIS/CDC-NCM composite over USB-C). Works, but means running the Pi off GPIO 5V (USB-C is busy talking to the phone) and doing configfs setup. Dongle path is strictly simpler.
  • CDC-ACM serial gadget with dash22b learning CdcAcmSerialDriver. Preserves auto-launch without a network stack, but forces every future data type through a single stream-oriented pipe. Networking gives multi-port for free.
  • USB-serial protocol emulation (Pi pretending to be FTDI/CH340). Doable via raw-gadget + shim, but purely to preserve the existing on-phone driver stack. Not worth it once dash22b is going to change anyway.

Protocol on the Ethernet link

Phone gets DHCP from dnsmasq on the Pi (Pi = 10.55.0.1, phone = 10.55.0.2). dash22b opens sockets to the Pi. Choice of application protocol is not load-bearing — three reasonable options:

  • WebSocket + JSON/CBOR — trivial to debug from a laptop with wscat.
  • MQTT (Mosquitto on Pi, Paho on Android) — nice topic structure (car/rpm, car/tpms/FL, car/dtc/...), easy fan-out to other logging tools.
  • gRPC bidirectional streams — typed schemas, best for bidirectional RPCs (dash22b requesting a Mode $06 pull, Pi streaming SSM back).

SSM data model

Pi owns the K-line, keeps a rolling cache of last-value + timestamp for every subscribed PID. dash22b subscribes to a set of PIDs at a rate; Pi streams updates. Phone never waits on the K-line, and the Pi can log at its native poll rate independent of what the dash is displaying.

Auto-launch details

Android does not fire an app-launch intent for "USB ethernet interface came up." So:

  1. USB_DEVICE_ATTACHED intent filter matching the specific dongle's VID/PID. Dash22b receives the broadcast, ignores the UsbDevice handle, and opens its TCP socket to 10.55.0.1. Cold-launch trigger.
  2. ConnectivityManager.NetworkCallback watching for a TRANSPORT_ETHERNET interface to come up — covers the "app already running, cable was just replugged" case.

Open questions before building

Smoke test to run first. Does the existing Y-adapter cleanly pass a USB Ethernet dongle on its data leg while PD input is active? Cheap 2-in-1 OTG adapters are hit-or-miss — some forward a simple FTDI/CH340 fine but choke on higher-power devices. Plug an RTL8153 or AX88179 dongle into the data leg with PD input powered, confirm Android enumerates it as usb0. If this fails, the whole Phase 2 plan needs a rethink.
  • Which dongle chipset — RTL8153 (gigabit), RTL8156 (2.5 GbE, headroom), AX88179A. All mainline-supported in Android. Prefer known-good over cheapest no-name.
  • Pi boot vs. phone DHCP race — Pi must be up with dnsmasq listening before phone tries to DHCP, or phone gets 169.254.x.x until next renewal. Fix: Pi boots off ignition-switched 12V a few seconds before the cable is expected to be plugged; dash22b retries the socket connect on a short interval (want this anyway).
  • dash22b transport interface — new RpiTransport alongside the existing serial one, behind the current datasource interface. Existing on-phone SSM code path stays as a fallback for when the Pi isn't present.

Phase 3 — Rear-view camera

UVC camera on a Pi USB-A port. Two options:

  1. Restream over the same Ethernet link as MJPEG or H.264 (ustreamer, gstreamer) — dash22b renders in a SurfaceView / ExoPlayer. Flexible, works over Wi-Fi too, easy to record on the Pi.
  2. Advertise f_uvc on a Pi gadget port — Android sees a webcam directly. Lower latency but locks to USB and re-introduces the gadget-mode complexity avoided in Phase 2.

Option 1 is the default. BLE cannot carry the camera stream (~1–5 Mbps at low latency, out of budget) — the Ethernet link is what unlocks this.

Phase 4 — Wi-Fi as a third transport

  • Same socket code as Phase 2, different route. Pi joins home Wi-Fi in the garage → pull logs from inside the house. Cable falls out → the app can fall back to Wi-Fi for SSM (camera would still need the cable due to bandwidth).
  • Alternatively, Pi runs an AP that the phone joins when cable's unplugged. Purely a bonus once the Ethernet path is stable.

Physical install sketch (end state)

  • Pi 4 in the glove box, powered from switched-12V glove-box tap via GPIO 5V pins through a proper buck converter (or a car USB-PD PSU into the Pi's USB-C).
  • Pi USB-A → K-line USB cable → OBD2 port.
  • Pi USB-A → rear-view camera (UVC).
  • Pi RJ45 → USB Ethernet dongle → phone Y-adapter data leg.
  • Car 12V → USB-PD supply → phone Y-adapter PD input.
  • Pi GPIO → relay board with hardware watchdog → door-lock control lines (spliced parallel to OEM RKE receiver outputs).
  • Onboard BLE + Wi-Fi handle door-lock service and Wi-Fi transport respectively.
